# PC 用户网页端下线决策（待确认）

状态：待产品决策。最后核对：2026-08-29。在作出明确下线决定前，`user-web` 仍是正式交付组件，必须继续参与发布、构建和回归检查。

## 评估范围

本文将“网页端”理解为 `ai-creator-server/user-web` 这个 PC 用户创作工作台，不包含管理后台 `admin-web`，也不包含 `uni-app` 小程序端。如果实际要下线的是管理后台，影响范围会完全不同。

## 当前架构事实

- `user-web` 是独立的 React + Vite 应用，包含邮箱登录/注册、AI 生图/生视频/漫剧、模板、作品/任务、工具、积分和个人中心。
- `server/src/index.ts` 根据 `WEB_APP_HOSTS` 将 `ooa8.com`、`www.ooa8.com` 请求分流到 `user-web/dist`；其他 Host 默认返回 `admin-web/dist`。
- 发布脚本、发布包检查脚本、更新包预检查和相关测试都要求 `user-web` 存在并生成 `user-web/dist`。
- 邮箱账号写入 `users.email`、`users.password_hash`，账号类型为 `email`，网页 token 使用 `clientType=web`。
- 小程序登录按 `openid` 查找用户；当前代码没有把“邮箱账号”与新的微信 `openid` 自动合并的逻辑。网页用户切换到小程序后，可能被创建成另一个用户，无法直接看到原作品、积分和会员权益。
- `model_tiers.web_visible/web_display_name/web_sort_order` 是网页端专用运营字段，但 `clientType=web` 不能全局删除：管理后台 token 也使用该值，任务接口还区分 `web/app` 的桌面端任务契约。
- `user-web` 源码已纳入 Git，且当前发布脚本、发布包检查、安装更新检查和部署文档都将其视为正式组件。下线前仍必须完成独立备份、迁移与回归，不应仅因源码已受版本控制就直接删除。

## 主要风险

| 等级 | 风险 | 可能后果 |
| --- | --- | --- |
| P0 | 账号和数据不可访问 | 网页邮箱账号没有 `openid`，直接关闭网页登录后，用户的历史任务、文件、积分、会员可能仍在数据库中，但用户无法通过小程序进入同一账号。 |
| P1 | 发布/更新流程失败 | 只删除 `user-web` 而不修改 `build-release.sh`、`inspect-release.sh`、更新包白名单和测试，会导致发布包构建或升级预检查失败。 |
| P1 | 误删共享后端能力 | `/tasks`、`/files`、`/templates`、`/tools`、会员、积分、队列和存储同时服务小程序；按“网页用过”来删除这些路由或服务，会回归小程序。 |
| P1 | 进行中任务和文件丢失 | 下线前删除 `uploads`、`files`、`ai_tasks`、`media_assets` 或队列清理逻辑，会影响异步任务结果、历史作品和文件权限。 |
| P1 | 域名和入口异常 | DNS、Nginx、SSL、`WEB_APP_HOSTS`、CORS/CSP 未同步时，网页域名可能展示后台、返回 503，或留下仍可注册/调用的孤立入口。 |
| P1 | 账号接口继续暴露 | 即使前端删除，邮箱注册/登录接口仍可能可用。若不明确停用策略，可能继续产生无法服务的新账号，也会增加垃圾注册和客服成本。 |
| P2 | 运营配置和维护负担 | `web_*` 字段、网页专用测试、文档和显示配置残留，会让后续维护人员误以为网页端仍受支持；但这些字段本身不应在第一阶段删除。 |
| P2 | 回滚与追溯不足 | 即使源码已受 Git 保护，未经独立发布基线、数据备份和回滚演练就删除网页端，仍会失去可快速恢复的线上交付版本。 |

## 推荐下线方案

建议采用“先软下线，后清理”的两阶段方案：

1. 先冻结网页端新增注册和新创作，保留一个短期的登录/历史数据访问窗口，显示迁移说明和小程序入口；保留数据库、上传文件、任务队列和必要的查询 API。
2. 在关闭前盘点网页账号数量、活跃会员、积分余额、进行中任务、历史文件和最近登录情况，并完成数据库、上传目录和发布包备份。
3. 设计账号迁移方案。最稳妥的是让已登录网页账号主动绑定微信 `openid`，或者由客服完成一次性绑定；不要假设同一邮箱就等同于同一微信用户。
4. 迁移窗口结束后，再关闭 `ooa8.com`/`www.ooa8.com` 的网页静态入口和 DNS/Nginx 路由，返回明确的下线页或 301 到说明页。API 不应直接跟随前端一起删除。
5. 最后再做代码清理：删除 `user-web` 构建和发布逻辑、网页静态 Host 分流、网页专用文档/测试，以及经过使用审计确认只服务网页的邮箱注册逻辑。

## 清理时的边界

可以考虑清理：

- `user-web/` 源码和构建配置（确认已归档并完成 Git 提交后）。
- `server/src/index.ts` 中的 `user-web/dist` 和 Host 分流。
- `scripts/build-release.sh`、`scripts/inspect-release.sh`、`update-package.service.ts` 中的 `user-web` 打包/白名单要求。
- `WEB_APP_HOSTS`、网页域名的 CORS/CSP/部署文档和网页专用测试。
- 邮箱登录/注册 API，但应先核对生产访问日志、是否存在其他 `app` 客户端，并给已有账号保留迁移或客服处理路径。

第一阶段不建议删除：

- `users.email`、`users.password_hash`、`account_type` 及其唯一索引。
- 已执行过的数据库迁移；不要通过 `DROP COLUMN` 回滚生产历史迁移。
- `ai_tasks`、`files`、`media_assets`、`creation_projects`、积分、会员、邀请、模板、队列和存储服务。
- 全局 `clientType` 类型和所有 `clientType=web` 字符串；应按 `role=user`、`role=super_admin`、`clientType=app` 等上下文逐项判断。
- `web_visible/web_display_name/web_sort_order` 数据列；可以先停用写入和读取，等确认没有回滚需求后再制定独立的数据清理迁移。

## 验收标准

- `admin-web` 和 `uni-app` 的登录、上传、创建任务、轮询、历史作品、模板、积分和会员流程不受影响。
- 网页域名返回明确下线页，不再返回旧前端，也不误返回管理后台。
- 已有网页账号、积分、会员、任务和文件都有可解释的去向；未完成任务能够完成或被明确退款/补偿。
- 发布包只构建并检查保留的前端，`server`、`admin-web` 和小程序相关检查全部通过。
- 数据库和上传目录备份可恢复，监控中没有新增网页专属 5xx、孤立注册或高频鉴权失败。
