# 项目代码与产品审计记录（2026-08-29）

## 结论摘要

当前项目可构建、静态测试通过，但“会员权益”存在严重的配置、展示与实际执行脱节：后台可以创建/修改权益项，小程序也可能展示它们，但除功能积分折扣和少量“是否为会员”开关外，绝大多数权益没有统一的服务端执行点。因此不能把当前任意新增的权益当作已交付的付费能力。

本次不删除任何文件、不修改业务数据。先完成 P0/P1 整改和会员商业规则决策，再处理文档归档、菜单合并及视觉优化。

## 审计范围与边界

- 覆盖仓库结构、文档索引、管理后台路由、小程序主要页面、服务端路由/服务/支付和会员调用链。
- 重点逐段核对了“后台配置 → 数据库读写 → 订单发放 → 用户资料/小程序展示 → 任务执行”的会员链路，以及工具、模型、支付、配置和输入表单链路。
- 未连接生产数据库，未调用真实模型、微信支付或微信开发者工具。因此“线上当前配置是否完整”和“真实支付回调是否成功”必须在脱敏的预发环境联调后确认。

## 当前不可用或不能承诺已可用的功能

1. 未配置主模型时，提示词优化和反推提示词的实际请求会失败；当前预检已明确报告该状态。
2. 任意后台新增的会员权益，除“功能积分折扣”和少量有效会员开关外，不能证明会在生成、去水印、队列、素材、商用授权等场景生效。
3. 支付若缺 APIv3 Key 或商户私钥，后台仍可能显示“已保存”，但下单会被服务端拒绝。
4. 脚本生成和提示词变体生成是已暴露 API/后台开关，尚不是小程序已发布功能。
5. 智能抠图只适合四角背景较一致的图片，复杂人像、发丝和主体贴边图片不可承诺有效。

## 会员整改的推荐顺序

1. **先做产品决策**：确认升级、降级、续费、叠加、退款、版本下线和权益变更对已购用户的规则。
2. **冻结高风险编辑**：已售套餐不可改 `version_id`；临时隐藏“新增自由权益”的售卖文案；月度积分在表单补齐前禁止保存。
3. **建立快照**：订单创建时保存权益、积分计划、价格和版本快照；支付回调和补发只从快照发放。
4. **统一 resolver**：以 `user_membership`/订单快照为输入，输出有效权益；会员页、资料页、任务、工具、支付补发全部复用。
5. **逐项接入执行**：先定义有限的 typed key，例如 `feature_discount`、`watermark_removal`、`tool_daily_quota`、`template_access`、`queue_priority`；每一个都有服务端检查和集成测试。
6. **再整理 UI**：小程序只显示 resolver 返回的权益和实际值；配置页使用“草稿 → 预览 → 保存”，保存成功后回读并显示生效版本。
7. **数据迁移与演练**：生产迁移前生成“模板/套餐/已购用户差异”报告，预发完成支付回调、补发、续费、降级、过期和退款回归。

## 建议新增的回归测试

1. 游客、登录用户、已购用户三种身份看到同一套餐的权益一致且无静态兜底承诺。
2. 修改模板值/图标/排序、禁用权益、删除权益后，所有套餐和资料页只显示 resolver 的结果。
3. 已售套餐不能换版本；后台更改后新订单与旧订单的快照互不影响。
4. 升级、降级、同档续费、重复支付回调、补发、退款、到期和月度积分各有端到端测试。
5. 每个可执行权益都验证“无权益被拒绝、有权益通过”，而不是只断言页面出现文字。
6. 后台连续编辑权益时验证请求顺序和版本冲突；支付配置缺密钥时不能开启。

## 后续实施前需要确认的决策

1. 已购会员的权益应完全冻结，还是允许未来的“全员福利”动态加到旧订单？
2. 用户有更高等级会员时购买较低等级套餐，应拒绝、排队生效、折算还是立即降级？
3. “永久会员”的有效期、可用模型/成本上限和供应商变更策略是什么？
4. PC 用户 Web 是继续维护、软下线，还是彻底下线？在有明确决策前不能删源码、构建流程或账号入口。
